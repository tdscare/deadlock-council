# Private offline Deadlock instance for scripted sandbox tests (researched 2026-10-23)

Nothing here was run in game. CONFIRMED = stated in a public source (URL given). UNVERIFIED = inferred, single unsourced user claim, or no source. Game build at last check: 6795 (Oct 17 2026), Nurse Harrow patch Oct 20 (a8/PATCH.md); Deadworks pins to specific builds, so check the release notes after each patch.

## Why `-insecure` fails for Kieran: no public answer
- No public source documents `-insecure` failing on the Deadlock client, or "Steam already running" / "only one instance" errors for it. UNVERIFIED which cause applies.
- What is public: the flag is a Source "no VAC" switch. A forum user in Sep/Oct 2024 says it lets the game open but "can't matchmake" (forums.playdeadlock.com/threads/game-crashes-on-launch-execept-with-insecure.25611, Sep 4 / Oct 4 2024; user claims). modlock README: "Clients run with -insecure and cannot join VAC-secured servers" (github.com/paralin/modlock). Neither says how to set it or why it would be refused.
- Related, different problem: Mar 12 2026 thread "Failed to create party queue ... only when launching through Steam" (forums.playdeadlock.com/threads/failed-to-create-party-queue-error-only-when-launching-through-steam.116802): launching through Steam threw "Cannot access SDR network. No ISteamHTTP."; running the exe directly from the install folder as admin fixed it for the poster and one other. No mention of -insecure. Shows Steam-launch vs direct-exe launch behave differently on some PCs.
- Ways to pass the flag (all UNVERIFIED for Deadlock; standard Steam behaviour): (a) Steam Library > right-click Deadlock > Properties > General > Launch Options: `-insecure -console`; (b) URL `steam://run/1422450//-insecure -console` (Deadlock app id 1422450 per docs.deadworks.net server guide); (c) .bat with Steam already running: `"F:\steamlibrary\steamapps\common\deadlock\game\bin\win64\deadlock.exe" -insecure -console`. Close every running Deadlock instance first. Record the exact error text from each; that is the data nobody has published.
- Key point: the recommended route below needs NO `-insecure` on the client.

## Q1. Local dedicated server joined from the normal client
CONFIRMED (docs.deadworks.net/getting-started/server-admins/run-a-server, fetched 2026-10-23):
- Windows, .NET 10 Runtime (x64), Steam account that owns Deadlock, about 35 GB free.
- SteamCMD app id 1422450 (the Deadlock id); log in, `app_update 1422450 validate` into a server folder (guide uses `D:\deadworks-server`); repeat after each Deadlock patch.
- Extract latest `deadworks-<version>.zip` from github.com/Deadworks-net/deadworks/releases into that folder; `deadworks.exe` ends up in `game\bin\win64\`. Latest release seen: v0.4.15 (Aug, year not shown).
- Guide's .bat options: `-dedicated -console -dev -insecure -allow_no_lobby_connect` plus `tv_citadel_auto_record 0 spec_replay_enable 0 tv_enable 0 citadel_upload_replay_enabled 0 hostport 27067 map dl_midtown`. Custom options REPLACE Deadworks' defaults, so give the full list.
- Port 27067 (TCP+UDP firewall rules only needed for other PCs; loopback needs none). Docker variant uses UDP 27015.
- Client connect: in console `connect <ip>:27067`; dev guide (docs.deadworks.net/getting-started/developers/setup): `connect localhost:27067`. Add `-nomaster` or set `unlisted: true` in `configs/deadworks.jsonc` so the server is not listed publicly (deadworks.net FAQ).
- The `-insecure` is a SERVER option. Deadworks public servers are joined by normal players from the console; deadworks.net FAQ: "Players don't need the launcher if a server uses none of its maps or addons." Docker page: server logs in to Steam anonymously "so Steam authenticates connecting players" (github.com/Deadworks-net/deadworks README). So a normal secure client joining an insecure server is the designed case. Not stated in one sentence anywhere, so treat "secure client works with localhost:27067" as UNVERIFIED until tried (high confidence).
- Dev flow alternative (same page): extract Deadworks INTO the live game folder, run `deadworks.exe` from `Deadlock\game\bin\win64`, then start Deadlock. NOT recommended: it modifies the main install (one line in gameinfo.gi is added only by the launcher/addons; the dev route's file changes are not fully documented).
- modlock (github.com/paralin/modlock): `modlock dev` / `modlock play` start a local server (`--port`, `--no-game`) and launch Deadlock through Steam to join; `modlock-host --game-dir DIR --map NAME(default dl_midtown) --hostport (27067)`; "Clients run with -insecure". Windows runs the server directly. So modlock needs the -insecure client Kieran cannot launch. Without the game it falls back to a stand-in player with no hero (no damage data).
- Linux/Docker option exists (Wine, ~40 GB), irrelevant on Windows.

Contradiction with HARNESS.md: Custom Match refuses replicated cvars and had physics/lag problems (forums thread 109576, 2026).

## Q3. Programmatic control (Deadworks C#, docs.deadworks.net, fetched 2026-10-23)
- Hooks (plugin-base): `OnLoad(bool isReload)`, `OnUnload`, `OnPrecacheResources`, `OnStartupServer`, `OnGameFrame`, `OnTakeDamage(TakeDamageEvent)`, `OnModifyCurrency(ModifyCurrencyEvent)`, `OnChatMessage`, `OnClientConCommand`, `OnClientPutInServer`, `OnClientFullConnect`, `OnClientDisconnect`, `OnEntityCreated/Spawned/Deleted`, `OnEntityStartTouch/EndTouch`.
- Damage: `public override HookResult OnTakeDamage(TakeDamageEvent ev)` runs for every hit; `ev.Entity` (victim), `ev.Info.Damage` (read/write), `ev.Info.Attacker` (nullable), `ev.Info.Ability` (nullable), `ev.Info.Ability?.SubclassVData?.Name`. Return `HookResult.Continue` / `Stop`. Dealing: `target.Hurt(100f, attacker: x)`, `TakeDamage(CTakeDamageInfo)`, flags `PreventDeath ForceDeath SuppressDamageModification ...`. Not documented: damage type, crit, resist fields, hero-vs-NPC flag (check `DesignerName`). Whether `ev.Info.Damage` is pre- or post-resist is UNVERIFIED.
- Events: `[GameEventHandler("player_death")]`, also `player_respawned`, `player_hero_changed`, `player_used_ability`, `ability_added`; full list deadworks.net/db/events. `player_hurt` not confirmed.
- Hero: `SelectHero(Heroes.Inferno)` (not immediate), `GetHeroPawn()`, `ResetHero(bool)`; items: `AddItem("upgrade_sprint_booster")` on the pawn after `OnceHeroInitialized` (heroes page; the generated CCitadelPlayerPawn page did not list AddItem, so signature UNVERIFIED); souls/ability points: `ModifyCurrency(ECurrencyType, int, ECurrencySource, bool, bool, bool)`; abilities `AddAbility(string, UInt16)` / `RemoveAbility(string)`. No SetLevel/SetHealth/teleport/cooldown API documented; use `Server.ExecuteCommand("givelevelupgold 35")` etc. (UNVERIFIED that cheat cmds run server-side without sv_cheats; set `sv_cheats true` first).
- Spawn: `CBaseEntity.CreateByDesignerName("npc_trooper")`, `CEntityKeyValues` (`SetString`, `SetVector`), `prop.Spawn(ekv)`; entity list deadworks.net/db/entities has `npc_trooper`, `npc_boss_tier2/3`, `npc_super_neutral`, `npc_player_bot_brain`, `info_ability_test_bot`, `hero_testing_controller`. Bots: `Server.CreateFakeClient("Bot")` returns slot or -1; `controller.IsBot`. LIMIT: GitHub issue #87 (Oct 20 2026) "Fake clients ignore movement and buttons written in OnProcessUsercmds" - bots cannot be driven; they can stand still as dummies and take damage (UNVERIFIED that CreateFakeClient + SelectHero yields a hero dummy). No documented ability-cast API; `player_used_ability` is an event only.
- modlock (alternative): `onDamage` (before hit, can change amount), `onDamaged` (after hit, health before and lost), `spawnNpc(class, unit, team, position)`, `player.giveItem`, `player.clearItems`, `player.selectHero`, `addBot(options)`, `player.removeBot()`, `createEntity`, `fireInput`. Mods are WASM (TS/Luau/Python), no file access.
- Logs: Deadworks: `Console.WriteLine` appears in the server console; `Server.AddEngineLogListener(OnLog)` receives engine log lines; admin logs `game\bin\win64\logs\admin\` (one file per day); no console-to-file path documented. A C# plugin is normal .NET so `File.AppendAllText` should work (UNVERIFIED; docs show no sandbox). Simplest: redirect stdout in the .bat (`deadworks.exe ... > run.log`) (UNVERIFIED that the console is stdout). modlock: `build/server.log`.
- Plugins: DLL into `game\bin\win64\managed\plugins\`, hot reload on replace; config `configs\deadworks.jsonc`. Docker only: `docker compose exec deadworks console <cmd>`; RCON TCP on game port when `RCON_PASSWORD` set (Docker page).

## Q4. Ban / safety
- CONFIRMED: no public ban report tied to running your own Deadworks/modlock server, and no Valve statement on it. Deadworks page and modlock README say nothing about bans. UNKNOWN, not "safe".
- Server-side only: a plugin runs in the separate server process; the client is the stock game. That is the lowest-risk shape (same reasoning as RISK.md rank c). The server installs into a separate folder via SteamCMD, so the main game files stay untouched (this is why the standalone install is recommended over the in-game-folder dev flow).
- `-insecure` client: modlock says it cannot join VAC-secured servers; the point of the flag is to stay out of VAC. Never queue matchmaking with it. The recommended route does not use it on the client.
- Contradictory/unconfirmed: unexplained 2024-25 perma-ban threads (RISK.md); anti-cheat added Sep 26 2024, VAC link unclear (invenglobal.com/articles/19036, Oct 7 2024). Deadworks login: SteamCMD needs Kieran's credentials (Steam Guard). Use a throwaway account that owns Deadlock if one exists (the Deadworks Docker page itself says "A throwaway account works"). Downloading the server with the main account is what the guide shows; no source says it is risky.
- Third-party binaries (deadworks.exe, modlock) are unsigned community software: run them offline or in a VM/separate Windows user if cautious.

## Q5. Headless / automatable
- Server side: yes. `deadworks.exe -dedicated -console ...` is a console process; a plugin can `Server.ExecuteCommand`, spawn, give items, log. Docker variant has `console <cmd>` and RCON. An agent can launch the server, read the log file, restart per scenario.
- Client side: NOT headless. Damage needs a hero pawn in the world. Options: (1) a human/GUI client connects once (`connect localhost:27067`, could be a `+connect 127.0.0.1:27067` launch option, UNVERIFIED) and the plugin drives everything else with `Server.ExecuteCommand` and `Hurt`/`TakeDamage`, which gives engine damage-pipeline numbers but not real gun/ability inputs; (2) use bots as targets only (they cannot be driven, issue #87). Scripted ability casts by a player: no documented API (UNVERIFIED); `Server.ClientCommand(slot, cmd)` runs a command in a player's console and might trigger ability inputs (UNVERIFIED).
- modlock `--no-game` is headless but has no hero, so no damage numbers.

## Ranked routes
1. Deadworks standalone server (separate SteamCMD folder, 35 GB), normal client with NO `-insecure`, `connect localhost:27067`, C# plugin logging `OnTakeDamage` to a file, plugin sets hero/items/souls, spawns dummies. Fixes the -insecure problem; server side scriptable and readable by an agent. Risks: Deadworks must support the current build (pinned per release; may lag after Oct 20 patch), fake clients can't be driven, secure-client-to-insecure-server join unverified on Kieran's PC, item/level API gaps.
2. Existing HARNESS route: stock client, Sandbox (`new_player_basics`), `exec` cfgs, `condump`/console log. Zero new software, lowest risk, but manual, damage lines unknown (PROBE 7).
3. Custom Match with cheats + `sv_cheats true` + bots (HARNESS plan B; cvar refusals, lag).
4. modlock local server with `-insecure` client: richest API (`onDamaged`, `spawnNpc`, `giveItem`) but blocked by the exact flag that fails for him. Revisit only if `-insecure` is fixed by one of the launch methods above.
5. Offline demo parsing (boon / deadem) as a read-only data source (RISK.md).

## Recommended single route
Route 1: install Deadworks as a standalone server in `F:\deadworks-server` (SteamCMD app_update 1422450 validate; unzip Deadworks into it), run the guide's .bat adding `-nomaster` and `hostport 27067 map new_player_basics` (try `dl_midtown` if the map is refused), launch the stock Deadlock client normally (no `-insecure`), press F7, `connect localhost:27067`. First test steps in order: (1) server starts and prints build support; (2) client connects, if refused record the exact message; (3) a 20-line plugin that `Console.WriteLine`s every `OnTakeDamage` with victim, attacker, ability name, damage; (4) `AddItem` / `ModifyCurrency` via `/chat` commands; (5) spawn `npc_trooper` or a fake-client dummy. Do not touch matchmaking while the server runs; restart the client between test and normal play.
